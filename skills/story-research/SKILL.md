# story-research · 挖掘

传记越厚，挖掘越准——先有传记和访谈作为「知道该找什么」的依据，检索才有命中率。
这个 skill 负责 data flow 里的「外部 context」：从用户的长期资料库（如知识库导出）里挖出
与传记相关的信息。**产出不落盘**：挖到的东西在会话内呈给用户确认，随后直接走 story-write
更新传记。

## 前置：挂载 sources

```bash
node skills/story-research/scripts/check.js
# --target=<目录>  指定外部语料的本地路径
```

脚本确保 `~/.storytelling/sources/<源名>` 软链有效（缺失自动创建、坏链自动重建），
输出挂载状态与 md 文件数。`ready: false` 时不要继续。
`sources/` 下可以并存多个源（Notion、Obsidian 导出、邮件归档……），按用户指定或逐个挖掘。

若语料来自 Notion 且本地导出已过期，增量更新走用户已有的同步工具（如 okfa），
本 skill 不做任何平台 API 二次开发；同步工具配置失效时请用户自行修正，不要猜测或绕过。

## 工作流

1. **明确挖掘目标**。三种来源：story-interview 产出的传记空白、近期 transcript 里的
   主题、用户直接指定的命题（如「查一下某段经历的细节」）。目标不明确时先问用户一句。
2. **先看结构，再下钻**。语料是数千个 md 的目录树，顶层与内部的分区方式因源而异——
   先 `ls` + 各级 `index.md` 摸清导航，识别出「关于个人经历/关系/思考」的高价值区，
   再下钻；纯知识库、收集夹类的分区记个位置即可。
3. **识别并跳过数据库行页**。导出里大量页面是数据库行（课程、日历条目、人物卡片、
   收藏项等），正文只有一两行或纯图片——这类页面只扫 `index.md` 拿清单和单行事实，
   不逐个深究；除非用户点名要挖某个数据库。
4. **多轮检索**。目录名下钻 + 全文检索结合：

```bash
grep -ril "关键词" ~/.storytelling/sources/<源名>/    # 大小写不敏感列出命中文件
rg -l --no-ignore -i "关键词|正则" ~/.storytelling/sources/<源名>/
```

   检索词要多样：中文名、英文名、别名、项目代号、地名、人名轮着来；一轮没命中不等于没有，
   换词再试。文件名里内嵌的日期（如图片文件名、截图文件名）常是事件时间的可靠旁证。
5. **通读命中文件**，筛出与目标相关的部分。注意导出文件是快照——文件里的时间信息
   （frontmatter、正文日期）比文件系统 mtime 可靠。正文为空的页面（如按年份/阶段
   预建的空占位页）很可能是**用户故意为传记留的占位**——这不是「没找到」，要记为
   「待访谈空白」汇报给用户，不要当成无效命中丢弃。
6. **区分事实与线索**：用户明确写过的是事实；只言片语、待办、草稿是线索。传记只收事实，
   线索要么向用户求证，要么放弃——research 不生产传说。同一事实出现**互相矛盾或「对外
   说法 vs 真实情况」不一致**时（如某段经历实际结束月 vs 合同月 vs 简历月），不要擅自
   取舍，把两说都呈给用户。
7. **一次性集中澄清**。所有存疑点攒齐后，在呈报挖到素材的同一份报告里**一次性列出**请用户
   澄清，不要挤牙膏式地问一次写一点。用户的澄清答复是最高优先级事实，当场记下。
8. **呈报与回流**：把挖到的信息按「与传记哪个部分相关、补了什么」呈给用户确认，确认后
   在同一会话内衔接 story-write（其 plan.js 会照常处理），把素材织入对应小节。
   挖掘本身不改任何文件。

## 要点

- **你是研究员，不是搬运工。** 检索结果要筛选、组织、与传记已有内容对照，不是把语料
  原文粘给用户。
- 语料里有大量与个人无关的内容（知识库、收集夹），检索时以「关于这个人」为准绳，
  无关命中直接丢弃。
- 找不到就明说找不到，附上试过的检索词——空手而归的诚实汇报比硬凑素材有价值得多。
- **呈报结构**：按传记的部/人生阶段（见 STORY.md）组织挖到的素材；事实与存疑分开列；
  最后单独列「待访谈空白」（检索无果 + 空占位页），供回流到 interviews 待访谈清单。
- 本 skill 只描述方法，不预设任何用户的私人目录名或分区结构——那些由每次会话的
  实际探索得出。
